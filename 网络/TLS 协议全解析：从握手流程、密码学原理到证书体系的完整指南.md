# **一、TLS 1.2 与 TLS 1.3：握手流程图与核心区别**





TLS 握手是客户端和服务器之间“建立安全通道”的过程。

它包含加密套件选择、密钥交换、证书验证等步骤。



下面分别用文字流程图说明。



![TLS 1.2 vs TLS 1.3 Full Handshake](https://raw.githubusercontent.com/genwilliam/picgo_img/main/img/differences-between-tls-1.2-and-tls-1.3-full-handshake.png)

## **1. TLS 1.2 握手流程图（Full Handshake）**





TLS 1.2 典型握手一般需要 **5-7 个往返包**（RTT），流程比较冗长：

```
ClientHello  ----------------------------->  
（支持的加密套件、版本、随机数）

                     <----------------------------- ServerHello
                                （选择的加密套件、随机数）

                     <----------------------------- Certificate
                                （服务器证书）

                     <----------------------------- ServerKeyExchange
                                （密钥交换参数）

                     <----------------------------- ServerHelloDone

ClientKeyExchange  ----------------------------->
（客户端密钥交换参数）

ChangeCipherSpec   ----------------------------->
（通知开始使用对称密钥）

Finished           ----------------------------->

                     <----------------------------- ChangeCipherSpec
                     <----------------------------- Finished
```

核心特点：



- 握手内容大量明文
- 需要多个往返，延迟较高
- 支持大量算法，但其中不少已不安全
- 可以使用 RSA 静态密钥交换（危险）
- 支持 renegotiation（容易出问题）





TLS 1.2 很成熟，但协议复杂度比较高，也导致了许多潜在风险。



------





## **2. TLS 1.3 握手流程图（Full Handshake）**





TLS 1.3 目标是减少复杂性，提高安全性，让握手变得更精简。



典型流程如下：

```
ClientHello + KeyShare  ------------------------->  
（包含密钥交换参数，支持 0-RTT）

                     <----------------------------- ServerHello + KeyShare
                                    （选定加密套件，返回密钥交换参数）

                     <----------------------------- EncryptedExtensions
                     <----------------------------- Certificate
                     <----------------------------- CertificateVerify
                     <----------------------------- Finished

Finished --------------------------------------->
（双方确认密钥）
```

握手包从 **5-7 个减少到 1-2 个**。

这是 TLS 1.3 延迟降低的关键原因之一。



特点：



- 默认加密握手内容
- 不再支持 RSA 密钥交换
- 删除了大量脆弱算法
- 默认要求 Perfect Forward Secrecy（前向安全性）
- 握手轮次减少，响应更快
- 引入 0-RTT





TLS 1.3 是对 TLS 1.2 的结构性简化与安全强化。







# **二、TLS 1.3 的 0-RTT：让 TLS 也能“秒开”**





所谓 0-RTT（Zero Round-Trip Time），指的是：



客户端在发起连接的第一个包中，就能携带应用数据，不用等待服务器回应。



这在 TLS 1.2 中是不可能做到的。





## **0-RTT 依赖什么？**





它依赖一个核心能力：



客户端之前访问过服务器，并保存了一个 **PSK（Pre-Shared Key）预共享密钥**。



流程可以理解为：



第一次访问：



1. Client 与 Server 完成一次完整握手
2. 双方生成 PSK
3. 客户端保存 PSK





第二次访问：



1. 客户端携带 PSK 发起 ClientHello
2. 直接发送加密数据（0-RTT）
3. 服务器如果验证通过，就直接进入通信阶段







## **0-RTT 的利弊**





优势：



- 极大降低延迟
- 特别适合重复访问的网站、CDN、API





风险：



- 0-RTT 数据可能遭遇“重放攻击”（攻击者重复发送数据）





因此：



- 0-RTT 适合幂等操作（GET）
- 不适合转账、登录等敏感动作（POST、PUT）





浏览器和服务器一般会限制 0-RTT 的使用范围。



------





# **三、TLS 密码学原理：ECDHE、密钥交换、会话密钥如何生成**





TLS 的核心目标是：

在不安全的网络上，建立一个安全的共享密钥。



要做到这一点，需要两类加密：



- 非对称加密（用于验证、密钥交换）
- 对称加密（用于大量数据传输）





TLS 主要解决的问题是：



“双方从未见过面，怎么安全地产生一个共同的密钥？”



答案就是：**ECDHE 密钥交换**。



------





## **1. ECDHE：现代加密协议的基础**





ECDHE 全称：



Elliptic Curve Diffie-Hellman Ephemeral



含义拆分：



- Diffie-Hellman：让双方在公开信道协商出一个共享密钥
- Elliptic Curve：算法基于椭圆曲线，速度快、强度高
- Ephemeral（临时）：密钥只用一次，保证前向安全





其行为类似：



双方各自生成一个秘密值，但是只公开一个“混淆后的数”，最终双方都能单独算出同一个共享密钥，但外人无法逆推出原始值。



数学原理不展开，只要理解：



- 即使中间人窃听所有握手内容，也无法算出密钥
- 服务器即使未来被黑，攻击者也拿不到过去的会话密钥（前向安全性）
- RSA 无法做到这一点，所以 TLS 1.3 彻底移除了 RSA 密钥交换





------





## **2. 密钥推导（Key Schedule）**





TLS 1.3 使用 HKDF（HMAC-based Key Derivation Function）来推导密钥。



流程类似：



1. 产生初始秘密（ECDHE 计算结果）

2. 输入握手随机数（ClientRandom、ServerRandom）

3. HKDF 逐层派生

4. 最终生成：

   

   - 握手加密密钥
   - 会话加密密钥
   - 0-RTT 密钥（如果有）

   





TLS 1.2 的密钥派生路径复杂得多，而 TLS 1.3 则极度简化。



------





# **四、HTTPS 证书：从申请到验证的一整套流程**





浏览器在使用 TLS 前，需要验证：



“你到底是不是你声称的那个服务器？”



这就是数字证书系统的作用。



------





## **1. 用户申请证书（向 CA）**





企业或个人可以向证书颁发机构 CA（如 DigiCert、Let’s Encrypt）申请：



- 提供域名
- 证明对域名有控制权
- CA 颁发证书





Let’s Encrypt 自动化协议 ACME 可以自动申请、自动续期。



------





## **2. CA 验证域名控制权**





常见验证方式：



- DNS 添加 TXT 记录
- 在服务器上传验证文件（HTTP-01）
- 使用 TLS-ALPN 方式





验证通过后，CA 会用其私钥签发证书。



------





## **3. 证书结构**





证书里面包含：



- 公钥
- 证书持有者（域名）
- 有效期
- 签发机构
- 签名（CA 私钥生成）





证书本身只是一个“身份证”。

而浏览器要验证它的有效性，需要“信任链”。



------





## **4. 浏览器验证证书链**





浏览器内置一批可信任的根证书（Root CA）。



流程：



1. 浏览器收到网站证书
2. 检查是否被可信 CA 签发
3. 检查证书链是否完整
4. 验证证书使用的域名是否匹配
5. 验证证书是否过期/吊销
6. 最终确认该网站可信





结果就是浏览器地址栏的“小锁”。



------





# **五、TLS 1.3 和 TLS 1.2 的核心区别总结（与上一文合并）**





结合本篇与之前内容，总结如下：

| **项目**       | **TLS 1.2**      | **TLS 1.3**    |
| -------------- | ---------------- | -------------- |
| 握手包数量     | 5–7 个           | 1–2 个         |
| 握手是否加密   | 大量明文         | 全程加密       |
| 密钥交换       | RSA + DH/ECDHE   | 只支持 ECDHE   |
| 前向安全性     | 可选             | 强制           |
| 加密套件       | 多而杂，有弱算法 | 极简且全部安全 |
| 是否支持 0-RTT | 否               | 是             |
| 性能           | 较慢             | 显著加速       |
| 安全性         | 高               | 更高           |

大方向可以概括为一句话：



TLS 1.3 删除了所有历史包袱，重新设计出一个更快、更安全、更现代的 TLS。



------





# **六、整篇总结：TLS 的核心思想**





TLS 的整个体系围绕三个核心原则：



1. **不相信网络**

   网络是不可信的，因此通信必须加密。

2. **不相信中间人**

   必须验证对方是谁，这需要证书和 CA 系统。

3. **不相信自己的未来**

   即便未来密钥泄露，也不能让过去的通信暴露

   这就是前向安全性（ECDHE 的存在意义）。





TLS 协议不断演进，但目标始终一致：

为开放的互联网，提供尽可能接近“绝对安全”的通信通道。
