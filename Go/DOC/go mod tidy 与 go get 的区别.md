# **go mod tidy 与 go get 的区别**



这两个命令都是围绕依赖做事，但它们的“性格”完全不同，一个像整理房间的主人，一个像采购食材的助手。它们看似都修改 go.mod，实际上目标完全不一样。



## **go mod tidy：整理依赖、清理垃圾**





go mod tidy 的核心逻辑只有一个：确保 **go.mod / go.sum 与代码实际使用的依赖完全一致**。



它会做两件事：



1. **把代码中用到，但 go.mod 里缺失的依赖补上**

   类似「我看你用了 gin，但是 go.mod 里没写，那我帮你自动补上」。

2. **把代码中没有用到，但 go.mod 里残留的依赖删掉**

   类似「你 go get 下来的依赖你又没用，那我帮你打扫掉」。





换句话说，tidy 的状态是：



> 你的代码需要什么，我就给你加；

> 你的代码没用到什么，我就替你扔。



tidy 是“同步代码实际需要的依赖”。



## **go get：明确地** **添加/升级**依赖



与 tidy 最大的区别是：

1. go get 是主动行为；

2. go mod tidy 是被动行为。



你通过 go get：



- 显式安装依赖（比如添加 gin）
- 升级依赖版本（比如升级到 gin v1.9）
- 降级依赖版本（比如固定 gin v1.8.1）





例子：

```
go get github.com/gin-gonic/gin@v1.9.1
```

tidy 绝不会帮你做这种事。

tidy 只负责“你用到了什么我就补什么”。



所以两者的关系可以一句话总结：



- **go get 是改变依赖版本、添加依赖的武器**
- **go mod tidy 是将 go.mod 调整到“刚刚好”的状态**





它们互补，但用法不应混淆。

# **什么情况会触发依赖重新拉取？**





不论你使用 go build、go install 或 go test，Go 都可能触发依赖重新拉取。关键是触发条件，你理解了触发条件，就理解了为什么 Go 会“突然开始下载东西”。



下面列出所有可能触发重新拉依赖的情况：





## **1. go.mod 里新增了一个依赖**





比如你执行：

```
go get github.com/gin-gonic/gin
```

Go 必须去拉这个包，没有疑问。





## **2. go.mod 里的某个依赖版本发生变化**





你升级或降级依赖：

```
go get github.com/some/pkg@v1.2.0
```

Go 会去远端获取新的 tag，并写入 go.sum。





## **3. go.sum 缺失某个依赖的校验信息**





比如你 clone 了一个项目，但 go.sum 没被提交，或你删除了它的一部分。



Go 会重新下载依赖，用于生成校验信息。





## **4. 依赖本地缓存（GOMODCACHE）损坏或删除**





你手动删掉：

```
~/go/pkg/mod/
```

下次 build 必定会重新下载。





## **5. 依赖中引用了新版本的 transitive dependency（间接依赖）**





你不用它，但别人用它，Go 需要保证版本链一致性，因此也会重新拉。





## **6. Go 版本变化导致标准库行为影响依赖解析**



例如从 go1.16 升级到 go1.19，某些依赖解析方式变更时，会重新拉取并更新 go.sum。





# **Go workspace 与 go install 的交互**





Go1.18 引入 workspace（go.work），它改变了多模块项目的依赖解析方式，也影响到 go install 的行为。



先说结论：



> 当 go.work 存在时，go install 更倾向于使用工作区中的本地模块，而不是远端依赖。



简单来说：



- **你自己在 workspace 里维护的模块，install 时会直接使用本地源码编译**
- **不在 workspace 里的模块，才会从 GOMODCACHE 或远端获取**





例如目录结构：

```
go.work
api/
utils/
cmd/
```

go.work 内容：

```
use ./api
use ./utils
```

现在，如果你执行：

```
go install ./cmd
```

cmd 依赖 utils，但因为 utils 在 go.work 里：



- Go 会使用 **本地 utils** 作为依赖，而不是使用模块缓存的版本。





更进一步说：



> go workspace 将你的多模块项目变成“单模块”，并强制 go install 使用你的本地源作为依赖来源。



这对于多仓、多模块、多服务的企业项目极为重要，因为它保证了开发者看到的行为一致，不会出现“本地是新代码，install 用的是旧远端版本”的混乱情况。

# **$GOBIN、$GOPATH/bin、GOMODCACHE 的关系图**





为了让路径结构一目了然，我用一个更接近实际的图来解释：

```
┌──────────────────────────────────────┐
│                Go                   │
└──────────────────────────────────────┘

                ┌────────────────────────────┐
                │         GOMODCACHE         │
                │   模块缓存：Go 下载的所有包 │
                │   例如: ~/go/pkg/mod/      │
                └────────────────────────────┘
                           ▲
                           │  go get / build 自动读取依赖
                           │

┌─────────────────────────────────────────────┐
│                 go install                  │
└─────────────────────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              │                           │
      ┌─────────────────┐        ┌──────────────────────┐
      │      GOBIN      │        │     GOPATH/bin       │
      │ (若设置则优先)  │        │ 默认安装位置          │
      └─────────────────┘        └──────────────────────┘
              │                           │
              └───────────────┬───────────┘
                              │
                       可执行文件全局调用
```

总结成一句话：



- **GOMODCACHE** 用来放源代码
- **GOBIN / GOPATH/bin** 用来放可执行文件
- go install 的产物一定去“bin”，不去“modcache”
- go get / build 的依赖一定去“modcache”，从不去“bin”





这就是整个路径系统的完整布局。
