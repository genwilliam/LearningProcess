# **Go 结构体中的下划线（**_）



#  字段用法详解







## **前言**





在 Go 编程中，下划线（_）常见于以下场景：



- 作为占位符忽略不需要的变量；
- 导入包时仅执行副作用（import _ "pkg"）；
- 类型转换或赋值时丢弃结果。





但很多人可能没有注意过，**下划线还可以作为结构体字段名**。尤其是 _<type> 这样的零值字段（常用 struct{}），它有一个特殊的用途：

**阻止结构体使用位置初始化（unkeyed literal），强制使用命名字段初始化（keyed literal）**。



------





## **1. 结构体比较：带 *_*与不带 **_的区别

### **不带**_**字段**



```
package model

type User struct {
    Name string
    Age  int
}
```

两种初始化方式都合法：

```
u1 := model.User{"Alice", 18}                       // 位置初始化
u2 := model.User{Name: "Alice", Age: 18}            // 命名初始化
```



### **带**  **_** **字段**



```
package model

type User struct {
    Name string
    Age  int
    _    struct{}
}
```

尝试初始化：

```
u1 := model.User{"Alice", 18}                      // ❌ 编译错误：too few values in struct literal
u2 := model.User{"Alice", 18, struct{}{}}          // ❌ 编译错误：implicit assignment to unexported field _
u3 := model.User{}                                 // ✅ 零值初始化
u4 := model.User{Name: "Alice", Age: 18}           // ✅ 命名字段初始化
```

## **2. 原理分析**



Go 语言的结构体初始化有两种形式：

1. **位置初始化（Unkeyed Literal）**

   - 必须为**所有字段**提供值，并按声明顺序赋值。
   - 适合本包内部快速初始化，但字段顺序变动可能引发错误。

2. **命名字段初始化（Keyed Literal）**

   - 按字段名赋值，顺序可任意，未赋值字段使用零值。
   - 可读性高、维护性好，推荐跨包使用。

   





当结构体包含 _ 字段时，会出现以下限制：

- _ 字段名是未导出字段（小写开头），因此在**其他包**无法直接赋值。
- 位置初始化必须为所有字段赋值，但由于 _ 不可赋值，导致编译器报错。
- 结果是，外部包只能使用**命名字段初始化**（忽略 _），或使用零值初始化。





这在 Go 规范中有明确体现：



> “A field or method whose name starts with a lowercase letter is unexported. Unexported fields cannot be set from outside the package.”

> —— *The Go Programming Language Specification*



## **3. 同包 vs 跨包的差异**

- **同包**

  在同一个包内，未导出字段可见，因此位置初始化依然可行：

```
e := Employee{"Bob", 25, struct{}{}}
```

- 不过这样做会违背加 _ 的初衷。

- **跨包**

  未导出字段不可见，位置初始化会直接报错，必须使用命名初始化：



```
e := model.Employee{Name: "Bob", Age: 25} // ✅
```

| **场景**   | **不带** _ **字段** | **带** _ **字段（同包）** | **带** _ **字段（跨包）** |
| ---------- | ------------------- | ------------------------- | ------------------------- |
| 位置初始化 | ✅                   | ✅                         | ❌                         |
| 命名初始化 | ✅                   | ✅                         | ✅                         |



## **4. 设计动机与使用场景**

### **设计动机**

- **强制命名字段初始化**：防止位置初始化带来的字段顺序依赖问题。
- **增强可读性**：显式指明字段含义，代码更易维护。
- **减少 bug 风险**：字段顺序变动不会影响初始化语义。

### **使用场景**

1. **公共 API 的结构体**

   对外暴露的结构体，强制使用命名初始化，避免外部包错误依赖字段顺序。

2. **版本迭代频繁的结构体**

   防止字段调整时引入位置初始化导致的参数错位问题。

## **5. 注意事项**

1. **_ 字段占用零空间**

   常用 struct{} 作为类型，不增加结构体大小。

2. **仅影响外部包**

   在同包内仍可位置初始化，需团队约定自觉使用命名初始化。

3. **可能触发 linter 警告**

   一些代码检查工具（如 go vet、Staticcheck）会提示 “composite literal uses unkeyed fields”，建议统一用命名初始化。

4. **不影响零值初始化**

   T{} 这种方式不受影响。

## **结论**

在结构体中添加一个 _ struct{} 字段，可以有效防止跨包时的**位置初始化**，从而强制外部包使用**命名字段初始化**。

这种技巧尤其适用于需要保证初始化安全性和可维护性的公共结构体定义。
