# **Go 中的** go install、go build与 **go get**



在 Go 的世界里，这三个命令表面上看起来类似，都能产生“某种二进制文件”或“拉某个包”，但它们扮演的角色完全不同，逻辑路径也完全不同。

尤其是在 Windows 下使用 go install 时，很多人第一次看到「自动出现在 PATH 里并且随处可执行」都会有种错觉：



> “它是不是帮我 build 了一下，然后顺便加进系统环境变量了？”



如果你也这样想——那一半是对的，一半又不太对。

这篇文档我们就把这个事情讲清楚，不绕弯子，但会把整个机制铺开，从源码构建，到模块下载，再到安装目的位置，让你彻底掌握三者之间的本质差异。



------





# **一、先把三个命令的“核心意图”区分开**





为了避免混乱，先给一个强而简单的定义：

| **命令**   | **目的**                                                     |
| ---------- | ------------------------------------------------------------ |
| go build   | 构建当前包（或模块）的二进制，但**不会安装**，也不会放到 PATH 目录 |
| go install | 构建 + 安装二进制到 $GOPATH/bin（Go1.17+：GOBIN / GOMODCACHE） |
| go get     | 拉取依赖（Go1.17+ 按语义分成两类：**管理依赖** 或 **安装工具**） |

一个构建，一个安装，一个下载。

理解这一点后，再看细节才能不乱。



------





# **二、go build**：只构建，不安装，也不改变任何依赖



go build 的功能非常纯粹，它做的事情只有两件：



1. 编译当前包（或你指定的包）

2. 生成一个二进制文件

   

   - 默认：丢到当前目录
   - 如果不是 main 包，则不生成文件，只验证能否编译成功



它**不会做**的事情包括：



- 不会把二进制放到系统 PATH
- 不会下载缺失的依赖（需用 go mod tidy 或 go get）
- 不会修改 go.mod
- 不会安装工具





简单来说，它是一个“临时构建工具”。

你 build 完成后，它生成的二进制如果你不手动移动，就只会呆在当前目录。



类似下面这样：

```
go build -o myapp.exe
.\myapp.exe
```

它不会自动进入系统能全局执行的目录。



------





# 三、go install：构建 + 安装（注意安装路径的规则变化）







## **1. Windows 用户最常见的问题**





在 Windows 下执行：

```
go install
```

构建成功后，你会发现生成的 .exe 自动出现在：

```
%GOPATH%\bin\
```

如果你的 PATH 里已经包含 %GOPATH%\bin，那么你就可以直接：

```
mytool.exe
```

随处运行。

所以不要误以为 go install 等于：



> go build + 把编译结果复制到 PATH + 帮我调整系统环境变量



其实它只是把文件放在固定目录，而 PATH 是否包含这个目录是你初始化 Go 环境时就做了的事情，不是 go install 做的。



## **2. Go 1.17 之后的变化：版本后缀机制**





Go 1.17 改变了安装工具的方式。



以前：

```
go get github.com/u-tool/cmd/tool
```

就能安装一个 CLI 工具，现在不行了。

必须：

```
go install github.com/u-tool/cmd/tool@latest
```

如果不加版本，会报错。



这是为了避免“依赖污染”：

工具的安装与项目依赖应当是两件完全不相关的事。



------





## **3.** **go install**的完整行为路径



执行 go install pkg@version 时，它会：



1. 读取模块

2. 下载缺失依赖（放入 $GOMODCACHE）

3. 编译 pkg 中的 main 包

4. 将生成的可执行文件放入：

   

   - $GOBIN（如果设置）
   - 否则 $GOPATH/bin
   - 否则报错（极少）

   



之后你就能直接运行它。



这就是“构建 + 安装”的本质。



------





# 四、go get：现在不负责安装工具了，只负责下载依赖





曾经 go get 是一个“万能命令”：



- 拉包
- 更新包
- 安装二进制





都由它干。

但随着 Go modules 的稳定，这种行为被认为是有风险的。



Go 1.17 起，它被拆分成两个职责：

| **目的**            | **推荐命令**           |
| ------------------- | ---------------------- |
| 更新依赖 / 添加依赖 | go get                 |
| 安装工具            | go install xxx@version |

换句话说：



go get 现在只负责 **依赖管理**。

它的行为主要是：修改 go.mod、下载依赖、更新版本。



例如：

```
go get github.com/gin-gonic/gin
```

go build 的时候需要的依赖不会通过 go get 触发，而是由 go mod tidy 负责清理和修复 go.mod。



------





# **五、三者之间的真正关系（核心思维框架）**





为了彻底分清楚，把三者的内部逻辑抽象为三个维度：



一、是否编译

二、是否安装

三、是否管理依赖

| **命令**   | **编译** | **安装** | **更新 go.mod** | **下载依赖**     |
| ---------- | -------- | -------- | --------------- | ---------------- |
| go build   | 是       | 否       | 否              | 否               |
| go install | 是       | 是       | 否              | 是（仅工具安装） |
| go get     | 否       | 否       | 是              | 是               |

一句话总结：



- go build 是构建
- go install 是构建 + 安装
- go get 是依赖管理





它们没有谁替代谁，而是各司其职。



------





# **六、那到底什么时候用哪个？**







### **1. 开发本地项目：**





你只想临时构建：

```
go build
```

你想生成一个能全局执行的工具：

```
go install
```

项目依赖缺失：

```
go get / go mod tidy
```



### **2. 安装一个第三方 CLI 工具：**





例如安装 swag、air 等：

```
go install github.com/swaggo/swag/cmd/swag@latest
```

不要用 go get。



### **3. 在 CI 环境构建项目：**



```
go build -o app
```

不会污染系统，也不会往 bin 目录塞东西。



# **七、一个更大层面的理解**





如果把 Go 的构建流程抽象成一个链条：

```
模块解析 → 依赖下载 → 构建 → 安装（可选）
```

那么：



- go get 负责 **前半段** ：模块与依赖
- go build 负责 **中间段** ：本地构建
- go install 覆盖了 **中间段 + 后半段** ：构建 + 安装





这就是它们在整个 “Go 模块化时代” 中的角色定位。





# **八、一个容易忽视的小点：为什么 Windows 用户更容易误会？**





因为 Windows 用户对“PATH”这个概念更敏感。

当 .exe 自动出现在全局可访问目录里，会误认为是：



> go install 帮我把路径注入进去了



其实：



- Go 安装时已经把 %GOPATH%\bin 加入 PATH
- go install 只是把构建产物扔进去
- PATH 的修改不是 run-time 的，而是 setup-time 的





Linux / macOS 用户通常习惯通过：

```
export PATH=$PATH:$(go env GOPATH)/bin
```

所以心理预期更明确一点。





# **九、一个全局性的建议**





在现代 Go（特别是 Go1.18+）中：



- 不要再把 go get 当成安装命令
- 不要将临时构建的二进制丢入 PATH
- go install 才是构建工具链的“正确出口”





尤其对于常用工具（protoc-gen-xxxx、swag、air、dlv 等），明确写出版本号非常重要：

```
go install github.com/cosmtrek/air@v1.45.0
```

可复现性就不会出问题。





# **十、总结**



- go build：构建当前项目，到此为止
- go install：构建并安装到 bin 目录，从此可全局运行
- go get：依赖管理工具，不负责安装 CLI 工具
