# **Go 里的 init：到底谁先跑，谁后跑？**



写 Go 写久了，会遇到一个问题：

init 究竟是在什么时机执行的？



尤其是这种情况：

```
package main

func init() { /* ... */ }

func main() { /* ... */ }
```

再加上各种三方包、自己写的子包、_ "xxx/yyy" 这种只为触发 init 的导入方式，顺序一乱，就容易心里没底(所以一般不建议直接用太多的init函数,这个init函数如果非要用,尽量不要依赖别的包)。



这篇就专门捋一遍：**init 的执行顺序**、**多包场景下的初始化流程**、**下划线导入的用法**，以及一些容易被忽略的细节和坑。



------





## **1. 先回答直觉问题：main 和 init 谁先执行？**





先给一个最常用的结论：



在一个最简单的程序里：

```
package main

func init() {
    // A
}

func main() {
    // B
}
```

运行顺序必然是：



1. 执行当前包（main 包）的变量初始化
2. 执行当前包的 init 函数
3. 执行 main() 函数





所以：



- init 一定比 main 先跑
- main 永远只跑一次
- init 可以在一个包里出现多次（甚至多个文件），但是每个 init 也只跑一次





注意一点：init 不是“全局最先执行”的那个东西，而是**每个包自己的初始化入口**。真正最先跑的是 runtime 初始化（在你看不见的地方）。



------





## **2. 引入其他包以后：谁先谁后？**





只要引入了其他包，这个问题就不再是“main vs init”，而是“**包之间的初始化顺序**”。



先看一个简单的情况。

```
// file: main.go
package main

import "example.com/mypkg"

func init() {
    fmt.Println("main init")
}

func main() {
    fmt.Println("main")
}
```

假设 mypkg 里也有：

```
package mypkg

func init() {
    fmt.Println("mypkg init")
}
```

执行顺序是：



1. 初始化 mypkg

   

   - 先做包级变量初始化
   - 再执行 mypkg.init()

   

2. 初始化 main

   

   - 先做 main 包的变量初始化
   - 再执行 main.init()

   

3. 最后执行 main.main()





串起来就是：

```
mypkg init
main init
main
```

原因很简单：**一个包要用到另外一个包，就必须先保证被依赖的包初始化完成**。

换到人话就是：你要站在别人的肩膀上，前提是对方先站稳。



------





## **3. 多个包，多层依赖：init 链是怎么走的？**





实际工程里很少只有一层依赖，通常是这样的：

```
main -> pkgA -> pkgB
             -> pkgC
      -> pkgD
```

大致顺序：



1. 先初始化最底层依赖（没有再依赖别人的包）
2. 然后一层一层往上初始化
3. 最后轮到 main 包





举个更具体的例子：

```
// main.go
package main

import (
    "example.com/a"
    "example.com/d"
)

func init() { fmt.Println("main init") }
func main() { fmt.Println("main") }

// a/a.go
package a

import "example.com/b"

func init() { fmt.Println("a init") }

// b/b.go
package b

import "example.com/c"

func init() { fmt.Println("b init") }

// c/c.go
package c

func init() { fmt.Println("c init") }

// d/d.go
package d

func init() { fmt.Println("d init") }
```

初始化顺序是：



1. c（被 b 依赖）
2. b（被 a 依赖）
3. a（被 main 依赖）
4. d（被 main 依赖）
5. main





打印顺序大致是：

```
c init
b init
a init
d init
main init
main
```

可以记一句话：



> 先初始化“被别人依赖的”，再初始化“依赖别人的”。



------





## **4. 同一个包里多个 init 怎么办？**





再收缩到单个包内来。



一个包可以：



- 有多个文件
- 每个文件可以有 0~多个 init 函数





那它们的执行顺序是什么？



规则大致是：



1. 先做包内所有 **包级变量初始化**
2. 再执行这个包内所有文件里的 init 函数
3. 文件之间的顺序由编译器确定（通常按文件名顺序，但不要依赖这个细节）
4. 同一个文件里的多个 init，按照代码出现顺序执行





简单理解：

**不要对多个 init 的精确顺序产生依赖**。如果真的有顺序要求，那就老老实实写成普通函数，在一个明确的地方调用。



------





## **5. 下划线导入：只为触发 init 的“幽灵依赖”**





很多第三方包会在 init 里做一些注册、钩子、驱动注入之类的操作。

但有时候你只想要它的副作用，不关心导出的标识符。这种场景很典型：

```
import _ "database/sql/driver/xxx"
```

这行的意思是：



- 编译器会导入这个包
- 会执行它的 init 函数
- 但不会在当前文件暴露任何标识符（你也不能用）





如果你不用 _，而是写成：

```
import "xxx"
```

但代码里完全没用这个包，编译器会报错：

```
imported and not used
```

所以有两类场景会用到 _ 导入：



1. 只要 init 的副作用，不需要使用 API
2. 一些框架式注册（比如 image 包的解码器，database/sql 的驱动）





可以记下这句话：



> 想“用包，但不想显式使用任何符号”，就用 _ 导入。



------





## **6. init 真的是“最先执行”的东西吗？**





这问题有点阴险。



如果只看我们自己写的 Go 代码，直觉上是：



> init 最先执行，然后才有 main。



但从整个程序的角度看，这句话并不准确。



真实顺序大致是：



1. Go runtime 自己先初始化（调度器、GC、栈、内存管理等等）

2. 按依赖顺序初始化各个包：

   

   - 包级变量初始化
   - 执行该包内所有 init

   

3. 所有包初始化完之后，最后才调用 main.main()





所以更精确的说法是：



- init 是**某个包的入口初始化函数**
- 并不是整个程序的入口
- 程序真正的起点在 runtime 里，只是我们平时看不见罢了





------





## **7. init 的边界与坑：能做什么、最好不要做什么？**





init 看起来很方便，但用多了很容易把程序搞得难以理解。几个常见的点：





### **1. 能做什么？**





一般来说，init 适合做：



- 包级资源初始化（日志、配置、注册、表驱动等）
- 注册某种实现到一个全局 registry 中
- 为导出的 API 准备必要的环境





换句话说：

你可以把一个包想象成一个“模块”，那 init 就像模块加载时的“构造函数”。





### **2. 不建议在 init 里做的事情**





不推荐：



- 读很重的配置（比如远程配置中心，大量 IO）
- 建立复杂的网络连接（长连接、重试逻辑等）
- 做太多不可预期的工作（包括 panic）





原因很简单：



- init 的调用顺序是由编译器和依赖关系决定的，不直观
- 出错时栈信息不好读，定位会比较难受
- 会让包的导入变得有副作用，增加耦合





如果你发现你在 init 里写了一堆逻辑，甚至开始 catch 错误、打印日志、重试，那基本可以考虑：这些逻辑是不是应该在 main 或业务层的“显式初始化函数”里做，而不是藏在 init 里。



------





## **8. init 不能被手动调用**





这一点很多人第一次看到会有点不适应。



- init 不允许带参数
- 不允许被手动调用
- 也不允许有返回值





它完全属于“编译器和 runtime 控制的生命周期钩子”。



如果你需要一个既能在包初始化时自动调用、又希望被手动触发的函数，正确做法是：

```
func init() {
    doInit()
}

func doInit() {
    // 真正逻辑
}
```

需要显式调用时，就直接调 doInit()，而不是想办法用 init。



------





## **9. 一个小小的整体思维模型**





把上面所有内容缩在一张心里图，可以是这样：



1. 程序启动 → runtime 初始化

2. 解析依赖关系，按“先被依赖的包，后依赖别人的包”的顺序：

   

   - 初始化每个包的包级变量
   - 执行这个包的所有 init

   

3. 所有包都 init 完成后，执行 main.main()





与之对应的几个原则：



- 想让某个包在导入时自动“插自己一脚”，就用 init
- 想只要副作用，不要显式引用，就用 _ 导入
- 希望别人能清晰看到逻辑入口，就少在 init 里做复杂事，多用显式初始化函数
